# CLAUDE.md

## Project Overview

Code Crumb is a zero-dependency terminal tamagotchi that visualizes what AI coding assistants are doing in real-time. It renders an animated ASCII face that reacts to lifecycle events (thinking, coding, reading, executing, errors, etc.) via hooks, adapters, and file-based IPC. Supports **Claude Code**, **OpenAI Codex CLI**, **OpenCode**, **OpenClaw/Pi**, and any tool that can pipe JSON events.

### Interactive Keybindings

| Key | Action |
|-----|--------|
| `space` | Pet the face (sparkle particles + wiggle) |
| `t` | Cycle color palette (default/neon/pastel/mono/sunset/highcontrast); no-op under `NO_COLOR` |
| `s` | Toggle stats (streak, timeline, sparkline) |
| `a` | Toggle accessories (hats, ears, etc.) |
| `o` | Toggle orbital subagents |
| `l` | Open session list |
| `↑↓` / `j/k` | Navigate session list |
| `Enter` | On the main row: pin / unpin it. On any other row: pin and promote it to the center |
| `h` / `?` | Toggle help overlay |
| `q` / Ctrl+C | Quit |

Any key closes the help overlay or the session list (so `h`/`?` is not a strict toggle once open). `Enter` on the main row pins/unpins it; on any other row pins and promotes (dissolve/swap/materialize animation). Selection is by session id, not row index, and only live rows are selectable (see Main Session Policy). Minimal mode (`--minimal` / `MINIMAL_BOOT=1`) disables every key except `space` and `q`. Each stdin chunk is split into keys by `splitKeys` (renderer.js, pure: CSI/SS3 sequences whole, else one code point) and each key is handled on its own, so a held arrow or a fast `qq` works.

### Color Palettes

6 palettes: **default** (original colors), **neon** (high saturation cyans/magentas/limes), **pastel** (soft pinks/lavenders/mints), **mono** (greyscale), **sunset** (warm oranges/reds/golds/purples), **highcontrast** (accessibility palette). Press `t` to cycle. All togglable preferences (theme, accessories, stats, orbitals) persist between sessions via `~/.code-crumb-prefs.json`. Indicators below the face box show `● accs` / `○ accs` and `● subs` / `○ subs`.

## Tech Stack

- **Runtime**: Node.js 18+ (no npm dependencies)
- **Language**: JavaScript (ES6+, CommonJS modules, strict mode)
- **Platforms**: Windows, macOS, Linux
- **Terminal features**: 24-bit ANSI RGB color, Unicode box-drawing characters, cursor positioning

## Architecture

### Event Flow

```
Claude Code hook  ─┐
Codex native hook ─┴→ update-state.js (--editor <name>)  ─┐
OpenCode          ──→ opencode-plugin.mjs → opencode-adapter.js  ─┤
OpenClaw / engmux ──→ adapters/*.js                              ─┴→ Session files (JSON) → renderer.js (fs.watch) → Terminal Output
                                                                    (+ the global state file, for tmux mode and external readers)
```

Claude Code and Codex CLI share **one** hook handler: Codex has native hooks (`~/.codex/hooks.json`) with Claude-Code-shaped payloads, so `node setup.js codex` registers `update-state.js` with an `--editor codex` tag on every command. Precedence for the `editor` field is `CODE_CRUMB_EDITOR` env > `--editor` arg > `claude`, and `modelName` defaults to the editor (a codex hook says "codex is coding"). `update-state.js` also falls back to the payload's own `hook_event_name` when no event positional is passed.

### File-Based IPC

State is communicated between the hook handler and renderer via JSON files:

- `~/.code-crumb-state` — the global state file. **The unified renderer no longer reads it**: the main face follows the chosen session's own file (see Main Session Policy). It is written by the *owning* top-level session's hooks — `shouldWriteGlobal` is cleared when the file already names a different live, unstopped session (under 120s old), so a parallel window's ordinary hooks never touch it, while every `SessionStart` force-takes ownership. Because ownership and attention are decided separately, tmux mode (`--tmux`, via `readState()` with no argument) and external readers can be reporting a different session than the center face is showing.
- `~/.code-crumb-sessions/{session_id}.json` — per-session state, for **every** session: the orbital subagents, the parallel editor windows, and the one the main face is currently following. Sticky fields set once and preserved across later writes: `taskDescription`, `parentSession`, `agentType`, `editor` (see Editor Provenance), `model` (see Model Identity), `lastPromptAt` (see Main Session Policy) and the team fields. A Claude Code subagent's file is named `{parentSession}-agent-{agentId}.json` (see Subagent Attribution).
  - `SessionStart` writes a session file too (`isSessionStart: true`), so a fresh window is a candidate for the center before its first tool call. It first unlinks any stale predecessor with the same id — **except** when `source === 'compact'`, which is the same live session restarting and must keep its sticky fields. A `compact` SessionStart also keeps `stats.session` (counters, clock, `activeSubagents`) — only other sources reset it.
  - A non-agent `Stop` writes `idle` / `between turns` with `turnEnded: true` and **no** `stopped` (the session is between turns, not over). Any event that is not turn-opening (`TURN_OPENING_EVENTS`: PreToolUse, UserPromptSubmit, SessionStart, SubagentStart, PreCompact, Setup, PostModelSwitch) carries it forward — a late `PostToolUse`, a background agent's `SubagentStop`, `TaskCompleted`, `PostCompact` — and the global file's `stopped` along with it (`carriesTurnEnd`). **How** it is carried depends on the face (`inheritedTurnEnd`): only a reward or an error (`TURN_END_SAFE_STATES`) carries `turnEnded`; any other face carries `turnOver`, because the renderer folds `turnEnded` into `stopped`, force-rescues every face outside `RESCUE_EXCLUDE` to "wrapping up", and shows a new idle + stopped write as responding — a `ConfigChange`'s `reading` after a Stop replayed the whole responding → done! celebration. The renderer reads `turnOver` as "not active" (the short idle timeout) but never rescues it; the next echo with a reward or an error turns it back into `turnEnded`. Four turn-opening events also happen *between* turns (`AMBIENT_EVENTS`: `PreCompact`, `PostModelSwitch`, `SessionStart`, `Setup` — a `/compact`, a `/model`, a subagent's own auto-compaction, which Claude Code sends with the parent's `session_id` and no `agent_id`): after a finished turn they carry `turnOver` instead of clearing it, and all but `SessionStart` re-stamp the global file's `stopped`. Clearing it left the face on the 45s thinking timeout with nothing to close the turn. A mid-turn compaction is still live work. `StopFailure` fires instead of `Stop` and follows the same contract: the session file gets `turnEnded`, the global file `stopped`, and the face stays `error`. Codex's `Interrupt` (its Esc, which runs no `Stop`) does too, as `error` / `interrupted` without breaking the streak. On a session file `stopped` is reserved for `SessionEnd` — the owner's late `PostToolUse` takes exactly the same path as a parallel window's (`turnEnded` carried forward), and the global file's `stopped` re-stamp is scoped to the global write through a separate `globalStopped` flag. Leaking it onto the session file retired a live window in the orbital loader: the policy dropped the attended session (auto-releasing any pin) and the center bounced away and back with two swap animations. The renderer folds `stopped || turnEnded` for the face.
- `~/.code-crumb-stats.json` — persistent stats (streaks, records, session counters). `normalizeStats` repairs whatever it reads: every field keeps its default's type (a string `"streak":"5"` concatenated to "51"; `activeSubagents: [null]` threw in every hook, which then fell back and never rewrote — so never repaired — the file), and the maps keyed by a session id or file name (`sessionCounters`, `frequentFiles`, `topLevelSessions`) have no prototype, so a session called `__proto__` or a file named `toString` is an ordinary key. Also `sessionCounters`, a per-session-id map `{toolCalls, filesEdited, start, commitCount, creditedMs, lastSeen, countedDay}` (24h TTL, 50 entries — over the cap, throwaway entries with at most one tool call go first, and an entry holding parked agents is never evicted — 200 files each). The helpers (`freshCounter`/`normalizeCounter`/`parkAgents`/`unparkAgents`/`pruneCounters`) live in state-machine.js and are shared by update-state.js and base-adapter.js, so adapters restore counters and park agents the same way. Session and global files report the writer's own counters; `stats.session` mirrors its owner's entry, switching ownership restores counters rather than zeroing them, `daily.sessionCount` goes up once per session id per day (`countedDay`; a legacy `counted: true` reads as counted today), and `creditedMs` stops the same time being added to `cumulativeMs` twice (adapters subtract it too). An ownership switch also **parks** the outgoing owner's `activeSubagents`/`subagentCount` on its counter entry (`_parkAgents`, capped at 32, stored only when non-empty) and restores the incoming session's (`_unparkAgents`). A lifecycle event from a parallel window skips the foreign-session classifier and takes `stats.session`, and that used to wipe a conducting owner's agents — its `SubagentStop`s then matched nothing.
  - **Session time** is credited by `creditSession` (state-machine.js, shared with the adapters) at a turn or session end, and an outgoing owner is credited up to its own last activity (`creditEndFor` → `min(now, lastSeen)`), never up to the moment another session takes over: a session that ended at 18:00 was added to the next morning's total ("62h 59m today" after a weekend). Adapter and Codex sessions credit their own time at a turn end too (`creditOwnerSession` in base-adapter.js) and count their commits. "Today" is the **local** calendar day (`localDay`), not the UTC one. `pruneCounters(map, keepIds, now)` never evicts the session whose hook is running. Over its 50-entry cap, `pruneFrequentFiles(ff, keep)` ages every other entry by one and never cuts the file just touched — a full map used to reject every newcomer in the same write that added it. A parallel window's edits count in the lifetime totals while the owner conducts.
- `~/.code-crumb-prefs.json` — persisted user preferences (theme, accessories, stats, orbitals toggle)
- `~/.code-crumb.pid` — renderer process liveness. The renderer rewrites it every `PID_HEARTBEAT_MS` (10s); `isRendererAlive(pidFile)` (shared.js) — the one check the hook, `launch.js` and the renderer's own start-up guard all use — treats a file older than `PID_STALE_MS` (60s) as a dead renderer's whatever process now holds that PID, a pid ≤ 0 as garbage (`kill(0)` would signal our own group), and `EPERM` from `kill(pid, 0)` as alive. They used to disagree about `EPERM`, so a stale file on Windows (a logoff delivers no signal) made every hook open a window that printed "already running" and closed. `spawnRendererWindow` (shared.js, used by autolaunch and `launch.js`) opens the window with `process.execPath` (the running node, so the new terminal needs no `node` on PATH), from `HOME`, through an absolute `cmd.exe` (`ComSpec`) and System32's `where.exe` for the Windows Terminal probe: a hook's cwd is the user's project, and cmd.exe looks there before the PATH, so a project's `where.bat`, `wt.cmd`, `node.cmd` or `node.js` (PATHEXT includes `.JS`) ran instead. `buildRendererCommands(platform, args, title, { nodeBin, cwd, cmdExe })` takes the same three.
- `~/.code-crumb-spawn.lock` — autolaunch spawn lock: when the renderer is down, parallel hooks all notice at once; `acquireSpawnLock` (O_EXCL, 5s staleness) lets exactly one of them open a terminal. Nothing deletes the lock, so every launch after the first is a stale takeover, and that takeover is exclusive too: only the hook that creates `<lock>.claim` (O_EXCL) may overwrite the lock, and only while it is still the stale one it saw (a plain overwrite let up to 3 of 8 racing hooks each open a window). A claim left by a hook that died mid-takeover is cleared once stale
- `~/.code-crumb-quit` — written by the renderer on every exit; while it exists autolaunch launches nothing. It is cleared by the next `startup` or `resume` `SessionStart` (the editor starting again: `claude`, `claude --continue`/`--resume`, `codex resume`) and by `setup.js --autolaunch`, so one closed window no longer disables autolaunch for good
- `~/.code-crumb-stats.lock` — stats read-modify-write lock: parallel tool calls fire parallel hooks that all read-modify-write the shared stats file; `acquireFileLock` (O_EXCL, 150ms wait, 2s staleness) serializes them so no counter increment is lost. A stale takeover renames the stale lock aside (atomic, so exactly one waiter moves it), re-checks what it moved (restoring it exclusively if it was in fact a fresh, live lock), and then retries the O_EXCL create. A create failing `EPERM`/`EACCES`/`EBUSY` also counts as held (`LOCK_HELD_CODES`): on Windows a lock its owner is unlinking sits delete-pending, and creating it then fails `EPERM` rather than `EEXIST` — about 0.2% of attempts under contention. Treating that as "proceed" ran the read-modify-write unlocked, which is why the 6-worker contention test used to fail intermittently on Windows CI. A hook that cannot get the lock in time proceeds unlocked rather than stalling the editor.

Every state/session/stats/prefs write goes through `writeJsonAtomic` (temp file + rename, direct-write fallback) so the watching renderer never reads a half-written file. A rename refused with `EPERM`/`EACCES`/`EBUSY` — Windows, while a scanner, the indexer or another hook holds the target without delete sharing — is retried up to 3 times 2ms apart before the direct write, which is exactly the torn write the function exists to prevent. The stats file's read-modify-write cycle is serialized behind `~/.code-crumb-stats.lock` (`acquireFileLock` / `withStatsLock` in shared.js), so parallel hooks no longer lose counter increments; atomic writes still prevent corruption. A hook that cannot take the lock within `LOCK_WAIT_MS` proceeds unlocked — the lock is a courtesy, never a reason to stall the editor or skip the hook's work.

#### Editor PID Liveness

State file writes include a `pid` field — the writer's parent PID (`process.ppid`) for per-event hook processes (codex-notify; update-state.js on Unix), or the adapter's own PID for long-lived wrappers (codex-wrapper). **On win32, update-state.js and the adapters (`pidField()` in base-adapter.js) write no `pid` at all**: the hook's ppid there is a transient `cmd.exe` shim that dies within milliseconds — useless for protection and a prime PID-recycling target — so those sessions rely on staleness timeouts (`ORPHAN_TIMEOUT`/`STALE_MS`).

PID liveness is **identity-checked**, not just existence-checked: `isOwnedByLiveProcess(pid, lastWriteMs)` in grid.js only lets a PID protect a session if the process's **start time predates the session's last write** (+1s slack) — a recycled PID always fails this because its process was born after the original writer died. Start times resolve asynchronously in a per-PID cache (batched PowerShell on Windows, `/proc` on Linux, `ps` on macOS; one outstanding exec at a time; 60s TTL closes the live→live recycle gap; a TTL-expired entry keeps its old value while a `refreshing` marker stops further callers re-queueing it during the in-flight exec — which used to trigger a redundant second batch — and the result replaces the entry). The platform resolver is swappable through `_setPidResolver` (a test-only seam; resetting it also clears the in-flight latch and queue, since `tests/run.js` runs every test file in one process), and `OrbitalSystem._sessionsDir` is the matching seam for the directory itself — null in production, and the three loaders (`loadSessions`, `loadSessionsAsync`, `_applySessionResults`) all read `this._sessionsDir || SESSIONS_DIR` so a test can point them at a temp home. Unresolved (`pending`) PIDs are protected as a safe default; unreadable start times (Access-Denied on elevated/protected processes) or missing exec capability protect only up to a 1-hour cap past the last write — a real editor refreshes its session file with every hook, so its orbital self-heals on the next write, while a ghost recycled onto a protected process must not be immortal. Every protection site goes through `pidProtects(pid, lastWriteMs, isChild)`: a **child**'s pid is its parent's editor, whose being alive proves nothing about the agent, so a child keeps PID protection for `CHILD_ORPHAN_TIMEOUT` past its last write at most — a missed `SubagentStop` (an Esc) left a ghost orbital for the editor's whole lifetime on Unix, and held the main face at "conducting 1" with it.

**Hostile files.** Session files are written by any adapter (README documents `model_name` as free-form), so both readers take nothing on trust. `MiniFace.updateFromFile` and `readState` keep only one-line strings (`detailText`, which strips C0/C1 controls) for every text field — an object `model_name` crashed the renderer at `.slice` in `_assignLabels`, at boot, every boot, until the file went stale, and a newline or ESC in a folder or branch name reached the terminal raw — and a state outside the theme table, or an inherited name like `__proto__`/`constructor`, reads as `idle` (`knownState`/`STATE_NAMES` in themes.js; every `themes[state] || themes.idle` lookup let those through as an object or a function). A file holding `null`, a number or an array is skipped by both loaders (the async pass used to throw inside an fs callback 2s after boot), an object `session_id` falls back to the file name (`sessionIdOf`), and the renderer's boot `loadSessions` and per-frame `orbital.update` are guarded like every other loader call. `_truncatePath`'s `~` compares case-insensitively on win32, where editors disagree about the drive letter.

The renderer uses the armed-PID mechanism to detect a crashed editor: a candidate PID is **armed** only if it is still alive 2.5s after first being seen in a write AND its start time predates the reporting write (arming defers while resolution is pending). When an armed PID dies without a Stop event, a sticky `editorDead` flag triggers the rescue cascade (responding → happy → idle) and allows a new session to be adopted as main. A write newer than anything applied clears a false `editorDead` (PID-reuse guard). A newer write that reports a *different* pid (the same session id resumed under a new editor process) retires the armed PID at once — `lastEditorPid = 0`, `editorDead` cleared — so the death check stops testing the old process while the new one arms.

A death is also recorded in the renderer-side `deadSessions` map (id → the write timestamp at death) by `markMainDead()`. `adoptMain` must clear `editorDead` on a swap, so without that record a crashed session looked live again and won the center straight back on attention, showing its last work state for ~90s. `policySessions` (pure, exported) builds the policy input and projects those ids as `stopped` until the session writes something newer; entries for vanished session files are pruned.

Since the main face reads a session file, `lastStopped` now also covers a plain **turn end** (`readState` folds `turnEnded` into `stopped`), and the death check is skipped while it is set. An editor that dies sitting between turns is therefore never seen as `editorDead` — it is demoted by staleness instead, and `applyMainPolicy` picks another session. That is the honest reading: a session waiting for its next prompt looks exactly like one whose window was closed.

#### Main Session Policy

Which session the center face follows is decided by `pickMainSession` in renderer.js — pure, exported, and table-tested. It takes `{ sessions, currentId, pinnedId }`, where each session is `{ id, parentSession, isTeammate, stopped, stale, attentionAt, lastUpdate }` projected from the orbital loader's faces by `policySessions` (which also applies `editorDead` and `deadSessions`), and returns `{ mainId, pinnedId }`.

- **Candidates** are the *live top-level* sessions: no `parentSession`, not a teammate, not `stopped`, not `isStale()`. A subagent or teammate is never chosen on its own. On win32 nothing writes a `pid`, so "live" there is purely the 90s `ORPHAN_TIMEOUT` write-silence bound: a session sitting on a permission prompt for longer than that stops being a candidate and hands the center to any window that is working, even though the face's own `waiting` hold runs for 30 minutes (`WAIT_HOLD_STALE_MS`). The two clocks answer different questions — "is this session still alive?" and "how long do we keep showing the wait?" — and only the first decides the center.
- `isStale()`'s short 10s completion cut (`STOPPED_LINGER_MS`) applies only to a **child whose parent is no longer fresh** (`!parentAlive`). A face is built from its file and judged in the same `loadSessions` pass, before any `tick()` has moved a reward state on, so the rule effectively only judges freshly built faces: applied to a top-level window it declared a live window dead at a cold boot for the crime of having last written `proud`, and applied to a child of a live family it dropped every agent whose last write was a reward at renderer boot (created and deleted every pass, `liveChildCount()` 0, conducting hold lost).
- The main session's file is **never unlinked** by either stale purge (sync and async alike), regardless of face state — on win32 its `MiniFace` goes stale 30s before the `STALE_MS` purge fires, and deleting the file the renderer reads dropped the attended window to attention 0 as soon as any non-`UserPromptSubmit` hook recreated it.
- **A live pin wins** outright — including a promoted child. The pin is released (`pinnedId` returned as `null`) the moment its session is stopped, stale or gone, so a promoted agent hands the center back when it finishes.
- **Attention wins otherwise**: the highest `lastPromptAt` (`attentionAt`). That field is stamped by `SessionStart` (not from `/compact`, save the no-predecessor case below) and `UserPromptSubmit` and is sticky, so it means "when the user last addressed this session".
- **Ties keep the current main.** With no current main (the first pick) a tie breaks on the newest write (`lastUpdate`).
- **No live candidate keeps the current main**, which then decays through its own `idleCascade`.

`applyMainPolicy()` runs at the top of `checkState()`, inside its own `try { } catch {}` (it sits above the main try, and a throw there would take the 15fps render loop with it), and returns early while a swap is animating. `adoptMain` also clears `cwd`/`gitBranch`/`frequentFiles` (`setStats` only assigns them when truthy, so the outgoing branch used to linger), and `_executeSwap` seeds `lastNewWriteAt` from the adopted write's own `timestamp` — otherwise later reads of that same write are never "new", `fileAgeMs` stays 0, and a face swapped in while `waiting` escaped the `WAIT_HOLD_STALE_MS` bound forever. It also seeds `face.lastStateChange` from that timestamp when the adopted state is a tool or a wait (a swap restarted "still running … Ns" at 0, and the 10-minute long-tool hold with it), and clears `face.stateChangeTimes` after its own `forceState`: caffeine counts the last 10s of state changes, which belonged to the session that left, so a face that had done nothing went "hyperdrive!" 67ms after arriving. The swap animation is **not** chrome: minimal mode runs the transition tick and the dim pass too, so a `--minimal` face dissolves and materializes when the center moves — it just draws no ring and no list. The **first** pick is silent (`adoptMain` directly); every later change animates through `SwapTransition`, whose `swap` frame calls `_executeSwap` → `adoptMain`. `adoptMain(id)` is the single place `mainSessionId` changes: it resets the per-session trackers together (`lastAppliedState`, `lastAppliedTimestamp`, `lastStopped`, `editorDead`, `lastEditorPid`, `candidatePid`, `lastNewWriteAt`, `lastMtime`, `lastForceReadTime`) and adopts the new session's `modelName`/`editor`/`cwd`/`gitBranch`, so a held work state or an armed PID can never leak onto the incoming face. (`candidateSince` and `candidateTs` are deliberately left alone: `candidatePid = 0` gates both, and the next write that reports a PID rewrites all three together.) A dead editor's children do not count (`liveChildren` is 0 while `editorDead`, for `idleCascade` and the status line alike): `needsRescue` already treats them as not running, and counting them lifted the rescued face straight back to conducting, round responding → done! → conducting every ~12s until they went stale. `checkState()` is guarded **whole** while a transition is active — the guard used to sit inside the mtime branch, so on the ~3 ticks in 4 where the file was unchanged the rescue block, the fresh-read block and `idleCascade` all still acted on the session that was leaving. The resize handler force-completes a transition, but runs `_executeSwap` only while `swapTransition.swapPending()` (still dissolving); after the swap frame it just cancels, so the swap never runs twice.

Pressing `Enter` on a non-main row sets `face.sessionListPromote` (a session id); the render loop turns that into `pinnedSessionId` and the policy does the swap. `Enter` on the main row toggles the pin. Manual promotion is therefore only a pin — there is no second code path that moves the center.

**Where `lastPromptAt` comes from.** `update-state.js` stamps it on `UserPromptSubmit` and on a `SessionStart` whose `source` is not `compact` — plus the one exception: a *compact* `SessionStart` that finds **no** predecessor session file stamps a fresh one, because there is nothing to carry and an unstamped file means attention `0`, i.e. never the center again. Adapters (`base-adapter.js`) have no memory between events — each event is its own process — so the session file is the memory: the stamp is set on the first event of a session, on the first non-turn-ending event after a file marked `stopped` (a new turn), or when a live previous file has no stamp at all (self-healing across an upgrade or an `error`-first session); otherwise the previous stamp is carried forward. Adapters follow the same contract as update-state.js: a turn end writes `turnEnded` to the session file and `stopped` only to the global file (tmux), and `stopped` on the session file is reserved for `session_end` — a turn-end `stopped` used to latch the adapter's `MiniFace`, drop it from the policy, release any pin on it and bounce the center away and back every turn. A new turn is detected by `stopped || turnEnded` on the previous file. A late `tool_end`/`PostToolUse` is not a new turn: it carries the old stamp and keeps whichever end the previous file records (`turnEnded`, or `stopped` after `session_end`), and `guardedWriteState` re-stamps the global file's `stopped` only for such a tool end (`opts.toolEnd`), so the next turn's first event clears it, as in update-state.js. The previous file also carries `model` forward, since `guardedWriteState` can only do that for the global-file owner. OpenClaw's `session_end` is no longer folded into `turn_end`. `codex-wrapper.js` is long-lived, so it stamps on `thread.started` and `turn.started` and attaches the stamp to every write of that turn; `turn.completed`/`turn.failed` write `turnEnded` (global `stopped`), and session-file `stopped` is written only when the wrapper closes. `codex-notify.js` never stamps — its only event *is* a turn end — and writes it as one (`turnEnded` on the session file, `stopped` on the global file).

**What the main face reads.** `readState(filePath = STATE_FILE)` takes a path: the unified renderer passes `SESSIONS_DIR/<safeFilename(mainSessionId)>.json`, tmux mode passes nothing and gets the global file. For the main face `stopped` and `turnEnded` both simply mean "the turn is over", so `readState` folds them into `stopped`. A *new* `idle` + stopped write (the session file's picture of a finished turn) is translated to `responding` / `wrapping up` so the existing responding → happy → idle reward cascade still runs on the big face. Which writes are applied at all is decided by the pure, exported `startupGate(ts, stopped, now, rendererStartTime)` → `apply` / `skip` / `record`. During the first 5s a finished turn, or a live write more than 15s older than the renderer, is **recorded** — never shown, but marked applied (`lastAppliedTimestamp`/`lastAppliedState`) — because a plain skip let the same old write read as "new" once the window closed: a finished turn replayed as responding → done!, a stale one as whatever tool it last named. After the window only writes from more than 120s before the renderer started are skipped.

#### Subagent Attribution (`agent_id`)

`agent_id` routing comes first and is authoritative. Every hook fired inside a Claude Code subagent carries the **parent's** `session_id` plus `agent_id` and `agent_type` — so without reading `agent_id`, an agent's entire turn lands on the main face. Such an event is routed to `~/.code-crumb-sessions/{parentSession}-agent-{agentId}.json` (`subagentSessionId`), never to the global state file and never to the parent's own session file, and the `classifyForeignSession` heuristic below is skipped entirely.

A subagent's tool calls count toward its **parent's** `toolCalls`/`filesEdited` (its entry in `sessionCounters`), and toward the lifetime totals and streak.

A parent tool call writes `subagent` / `conducting N` only when the newest active entry is a legacy synthetic (no `agentId`), and never overrides an `error`. With agent-owned entries the parent's own work passes through — it used to be masked by `conducting N` for the whole life of any agent, errors included — and the renderer's `liveChildren` hold fills the idle gaps.

The eleven events in `AGENT_EXCLUDED_EVENTS` (`SessionStart`, `SessionEnd`, `SubagentStart`, `SubagentStop`, `PreCompact`, `PostCompact`, `Setup`, `ConfigChange`, `InstructionsLoaded`, `StopFailure`, `PostModelSwitch`) keep their own handlers even when they carry `agent_id`. `Stop` is deliberately **not** in that set: a `Stop` carrying `agent_id` is the subagent's own turn ending, so it writes `responding` / `wrapping up` to that agent's orbital without `stopped`, and leaves the parent's records and the global state file alone. `SubagentStop` remains the retirement signal. When `activeSubagents` has lost the agent (a parallel window's lifecycle event resets `stats.session`), a `SubagentStop` with `agent_id` still retires the deterministic `{parent}-agent-{id}.json` if it exists and is not stopped, and every retirement write carries the agent's resolved `model` forward.

**Family heartbeat.** A subagent emits no hooks at all during a model turn, and a parent waiting on its agents emits none either — so mtime staleness alone cannot tell a live family from a crashed one (on win32 there is no `pid` to break the tie). The heartbeat runs **child → parent only**: every agent event stamps the **parent's** session file (`_touchSessionFile`) without rewriting it. "Parent file fresh" therefore means the family is alive, and a child orbital only earns the long `CHILD_ORPHAN_TIMEOUT` (15 min) window while its parent's file is fresh; a crashed parent goes stale on the normal `ORPHAN_TIMEOUT`/`STALE_MS` schedule and takes its ghost orbitals with it.

The parent → child direction is deliberately **not** symmetric. `_touchActiveSubagents` touches only the *legacy synthetic* entries (an `activeSubagents` entry with no `agentId`, from a `SubagentStart` that carried none): those have no writer of their own, so the parent — which already writes their state via `_writeSubagentToolState` — must keep their mtime alive too. An **agent-owned** entry is skipped, because a child must never be kept alive solely by its parent's activity. Composed with `grid.js`'s `updateFromFile` accepting a newer mtime on unchanged content, a bare touch alone made `isStale()` false, so a missed `SubagentStop` left a ghost orbital that the parent's own tool calls revived for the full `SUBAGENT_MAX_AGE_MS` window — and pinned the main face at `conducting N` for four hours.

**Conducting hold.** Because agent events no longer write globally, no new content reaches the main's own file between `SubagentStart` and `SubagentStop` (the family heartbeat touches its mtime but does not rewrite it, so its JSON `timestamp` does not move). `idleCascade` therefore takes `liveChildren` (from `OrbitalSystem.liveChildCount()` — children of the main session that are neither stopped nor stale, recomputed per read) and substitutes `subagent` / conducting for what would otherwise be a downward transition to `idle`/`sleeping`/`thinking`. Rewards, real work states and the long-tool hold all pass through untouched, and `waiting` outranks conducting while it lasts (an actionable "the editor needs YOU" must not be masked by ambient "your agents are busy"). The status line's "spawning N subagents" count uses the same `liveChildCount()` (it used to count every non-main face on the ring, parallel windows and other sessions' children included). Minimal mode passes 0 — it still runs the session loader and both directory watchers, because even a bare face needs a main session to follow, but it draws no ring and never counts children.

#### Parallel Session Classification (legacy, no `agent_id`)

This heuristic is now the fallback path, for hooks that arrive without `agent_id`. The shared stats file has a single `session` owner, so a hook arriving from a different session id while the owner has `activeSubagents` used to be classified as that owner's subagent unconditionally — misclassifying unrelated parallel editor windows (sticky wrong `parentSession`, stolen `taskDescription`, frozen stats, blocked main-face ownership, and false retirement of the real subagent's synthetic orbital). `classifyForeignSession` (state-machine.js) now distinguishes the two: a foreign session is **parallel** (independent top-level) if it appears in the `stats.topLevelSessions` registry (populated at `SessionStart`, which real subagents never fire; 7-day TTL, 200-entry cap via `pruneTopLevelSessions`), or if its session file's birthtime predates the earliest active subagent's `startedAt` (a real subagent's file cannot exist before its own spawn). Unknown birthtime (unsupported filesystem) falls back to subagent classification, so real subagent grouping never regresses. Parallel sessions do not steal `stats.session` while the owner is conducting, do not count into the owner's counters, and do not propagate tool state onto subagent orbitals. Top-level sessions (the stats owner, or a classified parallel session) carrying a stale `parentSession`/`taskDescription` stamp are healed on their next write; teammates keep their legitimately-set fields.

#### Editor Provenance

Every state/session write carries an `editor` field (claude/codex/opencode/openclaw/engmux) distinct from `modelName`: update-state.js writes `CODE_CRUMB_EDITOR || 'claude'`, adapters write their own identity, and engmux-adapter writes the `-E`/`--engine` dispatch target. The field is sticky (preserved by the global owner guard, `guardedWriteState`, and `buildSubagentSessionState`; update-state.js stamps it on every write, so it has no `STICKY_FIELDS` entry). Fallback session IDs are editor-prefixed (`opencode-47040`, not bare `47040`) so anonymous sessions are self-describing and never collide across editors — update-state.js mints the same `FALLBACK_SESSION_ID` in both its try and catch paths so one session never splits into two orbitals. On the read side, `MiniFace.updateFromFile` derives `editor` best-effort for legacy files (modelName-as-editor, then ID prefix). The session list (`l`) shows each session's editor tag dimmed on row 1 and prefers the full `taskDescription` on row 3.

#### Model Identity

**`modelName` is a misnomer.** In every production path it holds the *editor* name — `update-state.js` sets `DEFAULT_MODEL_NAME = EDITOR`, so "claude is thinking" was always naming the CLI, never the model. The real model is a separate sticky field, `model`, holding a display name (`Opus`, `Sonnet`, `Haiku`, `Fable`).

`prettyModelName(raw)` (state-machine.js, pure) maps a raw id to that name: it strips a bracketed suffix (`claude-opus-5[1m]`) and a vendor prefix (`anthropic/claude-opus`), then matches the `MODEL_FAMILIES` table. **An unrecognised id is returned verbatim** — `gpt-5` stays `gpt-5` rather than being prettified into a guess — and it never truncates. Producers produce, renderers slice.

**Acquisition, in the order it is tried.** Claude Code carries a model on no hook payload except the two that are about models; **Codex puts a required `model` on every hook payload** (0.156) and has no `PostModelSwitch`, and its rollout JSONL has no `message.model` for the tail read — so a payload `model` (or `to_model`) is taken on **any** event when present. It is free, and the only way a Codex session follows a `/model`.

- `SessionStart` has an optional `model` field, and `PostModelSwitch` has `to_model`. Both are **free** — a payload field, no file read. `PostModelSwitch` also fires with `source: 'resume'`, so a restored session re-stamps itself, and it is the only documented way to follow a `/model` switch. It is registered as the 22nd hook event and is deliberately **absent** from `CODEX_HOOK_EVENTS` (Codex does not fire it).
- A **subagent** gets none of that: `SubagentStart` is only `{agent_id, agent_type}`. Its model comes from its own transcript at `<dirname(transcript_path)>/<session_id>/subagents/agent-<agent_id>.jsonl` (`agentTranscriptPath`, which rejects any `agent_id` that is not `[A-Za-z0-9_-]+` — a path-traversal guard). Read on the agent's first tool event that finds a model, then sticky, so it costs **one bounded read per agent**, never per hook.
- `Stop` reads the *tail* of the main transcript, every turn, deliberately **not** gated on "no model known yet". An install predating the `PostModelSwitch` hook never receives a switch event, so a gate would pin the first model ever seen and keep displaying it confidently after a `/model` — and a stale label is worse than none. Re-reading once per turn self-heals, against a hook already dominated by `getGitBranch`'s child process.

`_readTranscriptModel(path)` (update-state.js) is the reader: the last `TRANSCRIPT_READ_BYTES` (32 KB) of the file, newest line first, at most `TRANSCRIPT_MAX_LINES` (200) JSON parses, never `readFileSync` — a transcript reaches megabytes.

It scans the **tail, always** — including for a subagent, where the head looks like the obvious choice and is wrong. A real agent transcript opens with attachment and context entries running 26–64 KB *per line*, so the first `message.model` sits far past any sane head window: reading the head found nothing on all five real agent transcripts sampled, while the tail found the model on all five. The model cannot change within an agent's run, so the newest line is just as true as the first. It skips ids starting with `<` — Claude Code writes `"model":"<synthetic>"` on entries no model produced (usage-limit notices, "No response requested."), often as the newest line. It also matches `message.model` specifically — a bare `"model"` string appears inside `attachment` entries, which are not it. Both traps have a regression test.

**The transcript's contents are not a documented interface** (the directory layout is; the JSONL shape is not), so every failure path returns `''` and the face simply falls back.

Stickiness is carried in four places, each load-bearing: `STICKY_FIELDS`; a clause in update-state.js's global-state owner guard (the global write happens *before* the sticky loop, so without it tmux mode would see the field blink — and when ownership comes back from another window, the model is taken from the session's own file, or tmux lost it for good); `buildSubagentSessionState`; and `guardedWriteState` in base-adapter.js. That last one is what makes `model` sticky on the **adapter** path at all — `writeSessionState` rebuilds its object from scratch, so nothing else carries it forward, and it matters concretely for OpenCode, whose plugin holds the model only in memory: a restart would otherwise drop the field from the session file until the next assistant message.

**Where it shows.** The main face's status line leads with it (`Opus is thinking`) — the name is capped at `MAX_STATUS_NAME` (16) *and* at whatever room the rest of the line leaves before the right edge, because the fixed cap alone still wrapped `gpt-5.1-codex-ma is running command` at 38 columns — and demotes the editor to a dim tag on the indicators row; a **child** orbital's row 5 shows it in place of the branch/cwd, which for a child is always its parent's and therefore redundant (a **top-level** orbital keeps the branch — a parallel window may be somewhere else); and the session list's info row gains a segment. Editors that cannot report a model are unchanged in every one of those places.

Other editors: `codex-wrapper.js` parses the `-m`/`--model` its own header has always documented (and which was previously forwarded to codex and dropped). The OpenCode plugin records `message.updated`'s `modelID` **without spawning anything** and stamps it onto the payloads already going out. engmux already holds a real model in `modelName` and is deliberately not wired up — a one-line change if wanted.

### State Machine

23 face states: `idle`, `thinking`, `responding`, `reading`, `searching`, `coding`, `executing`, `happy`, `satisfied`, `proud`, `relieved`, `error`, `sleeping`, `waiting`, `testing`, `installing`, `caffeinated`, `subagent`, `starting`, `spawning`, `committing`, `reviewing`, `training`.

States have minimum display durations enforced via a `pendingState` queue to prevent visual flashing. The timings live in one exported table at the top of face.js (`MIN_DISPLAY_MS`): **work** states are short (coding/committing/reviewing 1500ms; reading/searching/executing/testing/installing 1200ms; subagent/spawning 2000ms; training 2500ms) because every PreToolUse refreshes them anyway, while **reward** states (happy 4000, proud 4500, satisfied/relieved 2500) and error (4000) are long because they are the emotions the user actually wants to see; responding keeps 3000 (#67).

`COMPLETION_MIN_SHOW_MS` (1800ms) is the guaranteed on-screen window for a reward face. Inside it nothing but an error replaces it — the next work state is buffered and a newer completion is queued, not shown. After the window, whatever is queued flushes (`_flushPending`), so a reward never sits for its full min display while something newer waits. Work that arrives while a completion is already queued is remembered in `pendingWork` and promoted to `pendingState` when that completion lands, so a long-running tool is never lost behind a reward face; a completion arriving clears `pendingWork` (its tool is finished). Completions never bypass active work — they queue and show when the tool finishes. Same-state writes refresh `lastStateChange` and the detail text, so a reward face stays up with live detail while a burst of identical completions lands. A same-state **work** write is a new tool call, so it also drops a queued completion (and any `pendingWork` behind it) — otherwise fast Bash → `relieved` queued → a second Bash showed the stale reward over the running tool and broke the long-tool hold. `MiniFace.updateFromFile` does the same. Caffeine detection never fires (nor decays) while a `pendingState` is queued: a buffered `caffeinated` overwrote a queued `waiting`, so the permission prompt never showed. `face.forceState(state, detail, minMs)` applies a state immediately, skips the buffering rules, drops the queue, and records the change for caffeine detection — the renderer's rescue paths (missed Stop, dead editor) use it, except on `RESCUE_EXCLUDE` states, which include `error`: it decays by itself, and a late `PostToolUseFailure` after Stop must still show its error face.

The state sets `ACTIVE_WORK_STATES`, `COMPLETION_STATES`, and `INTERRUPTIBLE_STATES` are defined once in shared.js and imported by face.js, grid.js, and renderer.js; the renderer's `FRESH_READ_STATES` (states worth a fresh file read for a missed Stop) is derived from them so a new work state can never be forgotten there.

#### The Timeout Cascade (`idleCascade`)

`idleCascade` is pure and exported from renderer.js, so the whole timeout cascade is table-tested. It decides what a face does when no new write has arrived, and it carries three holds:

**Long-running tools.** A tool call can outlive the hook cadence — one `Bash` can run for minutes with no further event — so a work face is no longer degraded to `thinking` on the 8s `IDLE_TIMEOUT` alone. The work state is held while the main's session file still names that same unfinished tool and the session is active, up to `LONG_TOOL_HOLD_MS` (10 min). `responding` is excluded: it is in `ACTIVE_WORK_STATES` but is a post-turn state, never a tool. The renderer tracks the file's state in `lastAppliedState` alongside `lastAppliedTimestamp` for that comparison. Instead of the face going stale the **detail line escalates**: after `LONG_TOOL_ESCALATE_MS` (8s) `ClaudeFace#displayDetail()` appends `still running … Ns` (`render()` truncates the base detail, never the suffix), and after `LONG_TOOL_SWEAT_MS` (20s) sweat particles start.

Escalation is gated on `ESCALATING_STATES` (face.js), **not** on `ACTIVE_WORK_STATES` — the latter answers a different question (what may interrupt what), and borrowing it timed two states that are not tool calls. It is `ACTIVE_WORK_STATES` minus `NON_TOOL_WORK_STATES` (`responding`, `subagent`), derived by subtraction so a genuinely new work state is covered by default. `responding` is a post-turn state, which `idleCascade` already excludes from the hold for the same reason. `subagent` is written by `SubagentStart` and then re-asserted every frame by the conducting hold for as long as agents run, so a multi-agent session used to render `conducting 3 · still running … 240s` and sweat permanently. A `subagent` written by a real `Agent`/`Task` call *is* a running tool, but distinguishing the two is not worth it: each agent now has its own orbital showing its own live state, so a counter on the main face duplicates what is already on screen — while getting it wrong means hours of false distress.

**Waiting on the user.** `waiting` is held regardless of `sessionActive` and with no display-time cap, because an `idle_prompt` notification arrives *after* Stop — the face waits as long as the user does. Past `WAIT_ESCALATE_MS` (30s) it escalates: `displayDetail()` appends the elapsed seconds, `update()` swaps the small `question` particles for 2 bold `bigquestion` every 20 frames, `render()` pulses the status line bold+accent on a ~0.5s cycle, and the renderer flashes `? WAITING FOR YOU` in the terminal title on the same cycle via the exported pure `buildTitle(modelName, status, flash)`. The frame dedupe key is `title + output`, so a blink with an unchanged body still gets written. The one bound on this hold is **write silence**, not display time: once the editor has produced no new write for `WAIT_HOLD_STALE_MS` (30 min) the face degrades to idle. That bound is platform-independent and needs no `pid`, which matters because on win32 nothing else can distinguish a crashed editor from a patient one. It measures silence, not death — a genuine 31-minute wait drops to idle and recovers on the next write. The clock comes from `noteNewWrite(ts, lastTs, now, lastAt)`, which advances only when a write's own JSON `timestamp` moves forward, so the renderer's 2s forced re-read of an unchanged file cannot fake freshness. "Moves forward" is `isNewerWrite(ts, lastTs, now)` (pure, exported), used at every newness check in `checkState`: normally a greater timestamp (parallel hooks land out of order, and the older write must not win), but once the last applied write is more than `FUTURE_SLACK_MS` (60s) in the future — a clock stepped back by NTP or a resumed VM — any write with a different stamp is new. A single future-stamped write used to freeze the face until the wall clock caught up.

**`turnOver` is not active.** `sessionActive` is `!lastStopped && !lastTurnOver && !editorDead`: a `turnOver` face (a wait, a `/compact` between turns, an echo on a work face) takes the short idle timeout but is never rescued. `readState` keeps `turnOver` out of `stopped` for exactly that reason.

**Conducting.** See Subagent Attribution — `liveChildren > 0` substitutes `subagent` for a downward transition.

### Hook Events

Twenty-two hook event types are handled: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Stop`, `Notification`, `UserPromptSubmit`, `TeammateIdle`, `TaskCompleted`, `SubagentStart`, `SubagentStop`, `SessionStart`, `SessionEnd`, `PreCompact`, `PostCompact`, `PermissionRequest`, `Setup`, `Elicitation`, `ElicitationResult`, `ConfigChange`, `InstructionsLoaded`, `StopFailure`, `PostModelSwitch`. Tool names from all supported editors are mapped to face states via shared regex patterns (e.g., Edit/apply_diff/file_edit → coding, Grep/search_files/codebase_search → searching, Bash/shell/terminal → executing) — see Multi-Editor Tool Mapping. PostToolUse includes forensic error detection with 39 regex patterns (30 stdout, 9 stderr) guarded by 14 false-positive patterns. Guards apply **per line** — a guard only cancels an error match on its own line — and stdout patterns are skipped for read-only commands (cat/grep/head/tail/find, git diff/log/show…), whose stdout is content. Exit codes are inferred from text (`Exit code N`, `exit status N`, `exited with [code] N`; never a bare `returned N`) only for shell tools — and for a **read-only** command only from an editor's own trailer, a whole line first or last (`extractTrailerExitCode`): `grep -n "Exit code" x.js` prints matches that name exit codes, and they are content. Likewise a merge conflict is never read out of a read-only git command (`git log`, `git grep "CONFLICT ("`), and a `cd` failure only counts for a chain that has a `cd`/`pushd`/`popd` in it (`SHELL_MOVE_RE`) — `tail deploy.log` can print one too. Shell commands are classified on intent (`shellIntent`): a shell wrapper is unwrapped first (`unwrapShell`, at most twice, one level of quotes each: `pwsh`/`powershell [-NoProfile…] -Command|-c`, `cmd /c|/k`, `sh`/`bash`/`zsh`/`dash -c|-lc`, also named by a path such as `/bin/zsh -lc` or `"C:\Program Files\PowerShell\7\pwsh.exe"` — Codex runs every command through one, so the wrapper used to be the only word ever seen), quoted arguments are emptied, read-only segments dropped, and `git commit`/`push` checked before test/build/install, so a commit message naming a build still counts as a commit. The read-only table includes the PowerShell reads (`Get-Content`/`gc`, `Select-String`/`sls`, `Get-ChildItem`/`gci`, `Test-Path`, `Write-Output`…) and cmd's `findstr`. A build is judged by the command and its subcommand, never an argument (`isBuildCommand`): a build tool by name (`tsc`, `webpack`, `vite`, `make`…), or a subcommand-style tool (`npm`/`yarn`/`pnpm`/`bun`, `go`, `cargo`, `docker`, `dotnet`…) whose subcommand or `run` script is `build`/`compile`, past flags, flag values and workspace selectors — `rm -rf build` and `mkdir -p build` used to finish as "build succeeded". The failure patterns are linear-time (`(?<!\d)\d+\s+fail(ed|ing)` — 60,000 digits cost ~1.4s of backtracking before), and `stripAnsi` strips OSC sequences ending in BEL **or** ESC `\` (an OSC 8 hyperlink), in linear time. Segments split on `&&`, `||`, `;`, `|`, `&` and newlines, but never on the `&` of a redirect (`2>&1`, `>&2`, `&>file`) — splitting `grep x 2>&1` left a segment `1` that is not read-only, so an ordinary grep had its matches read as a failure — and `cd`/`pushd`/`popd` count as read-only. Install detection is one table (`isInstallCommand`) for both sides of a tool call; flags and workspace selectors may sit between the manager and its verb (`pnpm --filter web add`, `pnpm -r install`, `yarn workspace x add`), `npm ci` counts, and a bare `yarn` is an install. A failed `cd` (`cd: …: No such file or directory`) is still an error even though `cd` chains are read-only — adapters with merged output and no exit code rely on it. It also honours the `interrupted`, `isError`/`is_error`, and numeric `exitCode`/`exit_code` fields that `normalizeToolResponse` carries through — an Esc-interrupted command shows `error / "interrupted"`, not `relieved / "command succeeded"`. Claude Code's `PostToolUseFailure` carries **no** `tool_response`: it is `{tool_name, tool_input, tool_use_id, error, is_interrupt, duration_ms}` (checked against the 2.1.281 binary), so `normalizeToolResponse` reads the `error` string as the output and `is_interrupt` as `interrupted`, and `classifyToolResult` tests `interrupted` before the forced error flag. Edit diff counts come from Claude Code's `tool_response.structuredPatch` when it is present (`diffFromPatch` sums the `+`/`-` lines across hunks, so a same-length replacement reports `+1 -1`, not `+2 -2`); when no patch is available — other editors, `Write` to a new file — `diffFromInput` falls back to counting the edit's own inputs, including `MultiEdit`'s `edits[]` and `NotebookEdit`'s `new_source`. Only the two totals reach the state file; the patch itself is never persisted.

**Which editors fire what.** Claude Code fires all 22. Codex CLI's native hooks (0.156) cover 11 of them (`PreToolUse`, `PostToolUse`, `PermissionRequest`, `PreCompact`, `PostCompact`, `SessionStart`, `SessionEnd`, `SubagentStart`, `SubagentStop`, `UserPromptSubmit`, `Stop`) plus one of Codex's own, `Interrupt`, which it runs **instead of** `Stop` when the user presses Esc (and a failed turn runs neither) — it has no `Notification` and no `PostToolUseFailure`, so `setup.js codex` registers exactly those twelve (`CODEX_HOOK_EVENTS`; `OUR_COMMAND_RE` matches the union with `HOOK_EVENTS`). `hooks.json` is parsed leniently — checked against 0.156 with an unknown event key, every other hook still ran — so an older codex that does not know `Interrupt` ignores it. `Interrupt` writes `error` / `interrupted` and ends the turn like `StopFailure` (session `turnEnded`, global `stopped`) without breaking the streak; without it the face held "running command · still running" for the whole long-tool hold. Codex hooks need a one-time trust confirmation; `--dangerously-bypass-hook-trust` skips it in automation.

The newer hook events map to existing face states: `PreCompact` → thinking (with rain particles), `PostCompact` → satisfied, `PermissionRequest` → waiting (with question particles), `Setup` → starting, `Elicitation` → waiting (with question particles), `ElicitationResult` → satisfied/relieved, `ConfigChange` → reading, `InstructionsLoaded` → reading, `StopFailure` → error (breaks streak), `PostModelSwitch` → thinking `now <Model>` (see Model Identity). Of these, `PermissionRequest`, `Elicitation`, and `ElicitationResult` are per-session interactive events that route to orbital files in subagent context; the remaining 6 are system-level events excluded from subagent routing via the `LIFECYCLE_EVENTS` Set. `PostModelSwitch` is in neither group: it is kept out of `LIFECYCLE_EVENTS` on purpose (see Model Identity) so a parallel window's `/model` still classifies and cannot reset a conducting owner's stats. `WorktreeCreate`/`WorktreeRemove` are intentionally not registered because they replace default git worktree behavior.

**Answers.** A write that answers a prompt — `UserPromptSubmit`, `ElicitationResult`, a returning `AskUserQuestion` (PostToolUse or PostToolUseFailure), OpenCode's `permission.replied`, and the asking tool's own PostToolUse/PostToolUseFailure after a `PermissionRequest` (allowing it produces nothing else; the request carries no `tool_use_id`, so the session file keeps `waitingOn`, a digest of the tool's name and input from `toolCallKey`, until that call — never a parallel tool — finishes) — carries `answered: true` (one write, not sticky), and the renderer calls `face.dropWait()` before applying it: a wait still queued or remembered behind a reward is spent. It used to reappear the moment that reward ran out, "allow?" drawn again right after "got your answer".

**`workSince`.** A PostToolUse carries its tool's work state (`workState`/`workDetail`) so the renderer can inject a PreToolUse it missed, and — when the session file still holds that Pre write — the Pre's own timestamp as `workSince`. The renderer injects only if `workSince` is newer than the last write it applied (and never on a stopped write): a Pre it already showed was replayed after its reward, e.g. a Task's PostToolUse after its SubagentStop re-showed "spawning" for 8s over "agent done".

`UserPromptSubmit` → thinking (`reading your message`): the user just sent a prompt, so Claude is thinking before its first tool call — without it the face sat on happy/idle from the last Stop. The write carries no `stopped`, which also flips the renderer back to the active 45s thinking timeout. It also stamps `lastPromptAt`, which is what moves the center face to this session (see Main Session Policy). `Notification` is differentiated by `notification_type`: `permission_prompt` → waiting `allow?` (question particles), `idle_prompt` → waiting `waiting for you`, `elicitation_dialog` → waiting `needs input`, `auth_success` → satisfied `signed in`, anything else → waiting `needs attention`. The catch path (unparseable stdin) and `classifyTruncatedInput`'s event map cover the same events, including `UserPromptSubmit`, `TeammateIdle`, and `TaskCompleted`. That fallback path (`writeFallback`) also stamps `lastPromptAt` on `SessionStart` and `UserPromptSubmit` and writes `turnEnded` on `Stop`; with empty stdin it cannot see `source` (a fallback `SessionStart` always counts as attention) and takes the global file's owner id. It also serves payloads over 1 MB, whose envelope ids (`session_id`, `agent_id`, `agent_type`, `hook_event_name`) are regex-extracted, and payloads that parsed and then threw, whose parsed ids are reused rather than minting a `claude-<ppid>` phantom. When a `session_id` is known it is used as-is, `agent_id` routes to the agent orbital, the global file is written only by its owner, and sticky fields plus the turn-end carry come from the session file. All non-string payload fields go through `toText`. `UserPromptSubmit` and a `Stop` without `agent_id` register the session in `topLevelSessions` before classification, so a window opened before the hooks were installed is not mistaken for a subagent; the legacy synthetic-retire loop skips agent-owned entries.

`SubagentStart` carries `agent_id`, `agent_type`, `invocation_prompt` and `invocation_method` (there is no `description`, `prompt`, `agent_name` or `subagent_id`). `SubagentStop` carries `agent_id`, `agent_type` and `last_assistant_message`, and is matched by `agent_id` first, then a legacy `subagent_id`, and only FIFO when neither is present — so agents finishing out of order retire the right orbital.

`TeammateIdle` is agent-teams-specific (requires `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`). **`TaskCompleted` is not**: Claude Code's `TaskUpdate` fires it for any task marked completed, solo sessions included (verified in the 2.1.280 binary — no team check, `teammate_name` empty). Only a payload carrying `team_name` or `teammate_name` takes the teammate write; anything else falls through to the normal path (routed by `agent_id`, sticky fields preserved). Tagging a solo session `isTeammate` used to exclude it from the main policy for good. The teammate writes produce session files with `teamName`, `teammateName`, and `isTeammate: true` fields so team members appear in the orbital display with their designated name and a team-specific accent color.

### Orbital Label Priority

Each orbital subagent face displays a per-face label (max 8 chars). Priority order: `teammateName` > `taskDescription` > cwd basename > `modelName` > `sub-N`. For a top-level face, `modelName` is only used when the cwd basename is missing or shared with another orbital (the code used to put `modelName` first, so parallel windows in different folders all read `claude`). The `taskDescription` field is set once at `SubagentStart` and preserved across all subsequent session file writes; it comes from `subagentLabel` — the first non-empty line of `description` / `invocation_prompt` / `prompt`, whitespace-collapsed, ≤ 40 chars with a trailing ellipsis — falling back to `agent_type`, then the literal `subagent`. A sticky `agentType` field carries the Claude Code agent type (`Explore`, `Plan`, `general-purpose`, a custom agent name) and is used as the orbital's `modelName`. The live tool detail (e.g., "edit foo") shows separately below the label.

The row **between** the label and the detail (row `+5` of the 7-row `MiniFace`) is branch > cwd basename > theme status — **except for a child**, where a known `model` takes it instead (see Model Identity). A child shares its parent's repo and folder, so branch/cwd there is pure redundancy; a top-level orbital is a parallel window that may genuinely be elsewhere, so it keeps the branch.

Floating group labels (max 12 chars) use a separate priority chain via `_getGroupLabel`: `teamName` > shared non-default git branch > shared cwd basename > first member's `taskDescription` > first member's face label. Default branches (`main`, `master`, `develop`, `dev`) are excluded from the branch tier.

#### The Session List (`l`)

`OrbitalSystem` loads **every** session file into `faces`, the main one included; `setMainSession(id)` records which one it is and `getSortedFaces()` / `_assignLabels()` simply filter it out of the ring, so the main face is a normal `MiniFace` that the list, `liveChildCount()` and the policy can all read. `loadSessions(null)` (used at boot) excludes nothing. `MiniFace` carries `lastPromptAt`, `toolCalls` and `filesEdited` alongside the older fields for exactly this.

The overlay is built from three pure functions in grid.js:

- `orderSessionList(mainInfo, faces)` returns `[{ face, depth }]` in **tree order**: the main row first (a synthesized `mainInfo` object, not a `MiniFace`) with its children by `firstSeen` under it, then the other top-level sessions sorted by attention (`lastPromptAt` descending, `firstSeen` as the tiebreak) each followed by their own children, then any orphan whose parent is not on screen. `depth` is 0 or 1.
- `listNavigableIds(entries)` returns the ids `j`/`k` and `Enter` may land on: everything except a `stopped` row, plus the main row unconditionally (between turns the main's `stopped` is the folded `turnEnded`, and pin/unpin must keep working). A stopped session still *draws* — it lingers ~10s so the user sees it finish — but pinning it would be a no-op the policy undoes on the same tick, which reads as a dead key.
- `renderSessionList(cols, rows, entriesOrFaces, paletteThemes, mainInfo, selected)` draws them. `selected` is a **session id** (a number is still accepted for legacy callers, as is a plain face array in place of entries).

Each entry is `SESSION_LIST_ENTRY_ROWS = 4` rows:

1. `▸● statename  editor  ⊛/★/☆ label` — a child is prefixed with `└`. `★` marks the main row, `⊛` the main row while pinned, `☆` an independent top-level session on the ring. Width priority: the label is never sliced, the editor tag drops first, the state name truncates last.
2. `⎇ branch  ~/path`
3. the full `taskDescription`, else the live detail, else `waiting...`
4. the **info row**: `N tools · M files · model · age` for a top-level session, `<agentType | teamName | agent> · model · age ↳ parent` for a child. The model segment is omitted when unknown, and is pushed into `parts` **before** the join so the caller's `sliceToWidth(…, body)` still bounds the whole row. `formatAge(ms)` renders `3s` / `2m` / `1h`.

The footer says `⏎ pin` / `⏎ unpin` on the main row (by its pin state) and `⏎ pin+promote` on any other. Below `MIN_SESSION_LIST_ROWS = 12` (chrome + footer + both overflow marks + one entry) or `MIN_SESSION_LIST_COLS = 50` the overlay draws nothing at all; above it, `maxVisible` is derived from the row budget so the box can never outgrow the screen. `sessionListFits(cols, rows)` (grid.js) is that test, and it also gates the `l` key, the `l` hint (`fitKeyHints(width, omit)`) and a resize while the list is open (which closes it): an invisible list swallowed the next key, and an Enter silently pinned. The main row's ended marker reads the main file's own SessionEnd flag (`readState`'s `sessionEnded`, tracked as `lastSessionEnded`), because the stopped `MiniFace` is purged after its 10s linger and the ended row then came back as live, offering a pin.

### Orbital Grouping

Orbital faces that share a group key (`teamName || parentSession || sessionId`) are visually clustered through four layers:

1. **Cluster positioning** — group members sit `INTRA_GROUP_GAP` (0.35) apart and the groups share the rest of the circle evenly (all-singletons is exactly even). Every angle is a **box-arc angle**, not a geometric one: see Orbit Geometry below. No neighbour pair is ever closer than the orbit's `minGap`, and if `minGap` cannot be honoured the spacing degrades to even.
2. **Group tethers** — dim dashed `·` lines chain sequential siblings (A→B, B→C) at `TETHER_BRIGHTNESS = 0.15`; team groups use the team accent color. Tether dots skip ALL face bounding boxes (not just endpoints). Spawning faces are excluded from tether segments.
3. **Floating group labels** — short label text positioned below each multi-member cluster at `GROUP_LABEL_BRIGHTNESS = 0.45`. Team groups show the team name; non-team groups select via priority chain: shared git branch > shared cwd basename > first member's taskDescription > first member's face label (see Orbital Label Priority). Spawning faces are excluded from label extent calculation. Labels skip the main face exclusion zone.
4. **Overlap resolver** — post-position iterative nudge pass (max 3 iterations) that detects bounding box collisions between orbital faces and pushes them apart, re-clamping to terminal bounds. With box-aware spacing it is a safety net that should never fire; when it did fire every frame it was the source of the ring's jitter.

#### Orbit Geometry

The layout used to "glitch around" at many window sizes. A layout probe (virtual terminal, 600 sizes × 3 face counts × 240 frames) found four independent causes, all fixed:

- **The key-hint bar overflowed the last row.** At ~72 columns it wrapped on any narrower window, and a wrap on the bottom row scrolls the whole screen up a line on every changed frame. `fitKeyHints(width)` (face.js, pure) now fits it to `cols - 1`, dropping hints lowest-priority first (`t` theme goes first, `h` help last).
- **The orbit was sized from the current accessory.** Every state change could flip the same window between the orbit and the side panel. ClaudeFace now publishes `lastPos.keepOut`, a **worst-case** footprint (tallest accessory via `MAX_ACCESSORY_H`, the bubble's 4 rows above, `MAX_DETAIL_W` 36 columns, the stats rows below) that changes only with the terminal size or the `a`/`s` toggles. `keepOutOf(mainPos)` derives one from a bare box for older callers.
- **The thought-bubble nudge teleported faces.** It is gone. The renderer now draws the ring **first** and the main face over it, so an orbital drifting behind a bubble is occluded instead of shoved (and the help overlay now covers the ring, which it did not before). The side panel's right column comes from the keep-out, not the bubble, for the same reason.
- **Faces were spaced by angle, not by box size.** An 8×7 box needs 9 columns of travel along the top but only 8 rows along the sides, so even angles collided near 0 and π and the overlap resolver fought it every frame.

`computeOrbit(cols, rows, keepOut)` (grid.js, pure; `calculateOrbit` caches it per size + keep-out) centres the ellipse on the keep-out and requires the expanded rectangle's corner to lie inside it, which guarantees that no box on the ellipse touches the keep-out. It reserves the last row for the hint bar. It then builds a 720-step lookup of cumulative **box-arc length** (each step costs `max(|dx|/(MINI_W+1), |dy|/(MINI_H+1))`), from which it gets `maxSlots = floor(perimeter / ORBIT_SPACING)` (capped at `MAX_ORBITALS`), `minGap`, and `thetaAt(u)`. Rotation and every orbital offset live in that uniform `u`, so a gap of `minGap` is a real on-screen gap at every rotation.

The trade-off is that the ring now needs space to genuinely fit: roughly 80×60 or 114×50 with accessories on, and 78×60 or 104×50 with them off. Smaller windows get the side panel, which is stable. The old code "fit" at 60×45 because it let orbitals sit on the stats rows and accessories. `tests/test-grid.js › layout invariants` sweeps sizes and asserts no overlap with the keep-out, with each other, or with the hint row. It also checks that no frame-to-frame jump exceeds 3 cells, that the orbit is independent of state, accessory and bubble, and that nothing is written to the last cell of the last row.

Singleton groups (one member) get no tethers or labels. When all faces are ungrouped, spacing degrades gracefully to near-even distribution identical to pre-grouping behavior.

### Multi-Editor Tool Mapping

Tool name patterns are defined as shared constants (`EDIT_TOOLS`, `BASH_TOOLS`, `READ_TOOLS`, `SEARCH_TOOLS`, `WEB_TOOLS`, `SUBAGENT_TOOLS`, `REVIEW_TOOLS`, `ASK_TOOLS`, `SKILL_TOOLS`, `PLAN_TOOLS`, `PUBLISH_TOOLS`) in `state-machine.js`. Each pattern matches tool names from Claude Code, Codex CLI, OpenCode, and OpenClaw/Pi, including the current Claude Code set: `NotebookEdit` → coding; `NotebookRead`/`ReadMcpResourceTool`/`ListMcpResourcesTool` → reading; `LS`/`ToolSearch` → searching (`LS` with a path shows `listing <dir>`); `KillShell`/`BashOutput`/`EnterWorktree`/`ExitWorktree` → executing; `AskUserQuestion` → waiting `asking you` (question particles) then satisfied `got your answer`; `Skill` → reading `skill: <name>` then satisfied `skill loaded`; `TodoWrite`/`EnterPlanMode`/`ExitPlanMode` → thinking `planning` and `CronCreate`/`CronList`/`CronDelete`/`ScheduleWakeup` → thinking `scheduling`, both → satisfied; `Workflow`/`SendMessage`/`ListAgents`/`TaskOutput`/`TaskStop`/`Monitor` → subagent (`orchestrating` / `messaging an agent` / `checking on agents`), and a returning `Agent`/`Task`/`Workflow`/`TaskOutput` → happy `agent done` (the others → satisfied `checked in` / `message sent`) — except a background agent's result (`status: 'async_launched'`, Claude Code's default, returned at launch; checked against the 2.1.281 binary) → satisfied `agent launched`; `ReportFindings` → reviewing then satisfied `reviewed`; `Artifact`/`SendUserFile` → coding `publishing` / `sending a file` then proud `published` / `sent`. `patch` is an edit tool (it was unreachable in `REVIEW_TOOLS`).

MCP tools (`mcp__<server>__<tool>`) are classified by verb: `read|get|list|fetch|describe|inspect|check|show|view|download|export|whoami|debug` → reading, `search|find|query|lookup` → searching, `create|update|write|modify|edit|insert|delete|remove|append|set|move|replace|format|batch|push|merge|upload|import|add|manage|resize|copy|draft` → coding, anything else → executing. The detail is `server: tool` with `plugin_` stripped, a doubled `x_x` collapsed (`plugin_github_github` → `github`), and underscores turned into spaces; completion is satisfied `<server> done`. Anything unmatched shows `humanizeToolName(name)` (`AskUserQuestion` → `ask user question`) instead of the raw identifier. Every text-ish input goes through `toText` (strings pass, numbers stringify, objects/arrays/null → `''`), so a structured `command`, `file_path`, or `stdout` never throws inside `stripAnsi`. The `modelName` field in state files controls the display name (e.g., "claude is thinking" vs "codex is coding" vs "openclaw is reading").

#### Codex `codex exec --json` items

`codex-wrapper.js` parses the real ThreadEvent schema (codex-cli 0.146): thread/turn events plus typed items, each classified by `classifyItem(item, phase)` into the same tool tables above.

| Item type | Mapping |
|---|---|
| `command_execution` | `Bash` + the command text (so the Bash tables still split executing / testing / installing / committing); `declined` → relieved, `failed` → error via `isError`/`exit_code` |
| `file_change` | `Edit` over `changes[].path`; completed → proud `saved <file>` / `saved N files` |
| `mcp_tool_call` | `mcp__<server>__<tool>` through the MCP verb classifier |
| `web_search` | `WebSearch` |
| `collab_tool_call` / `collab_agent_tool_call` | `Task` — Codex's own delegation |
| `todo_list` / `plan_update` | `TodoWrite` → thinking, then satisfied `plan updated` |
| `context_compaction` | thinking `compacting memory` → satisfied `memory compacted` |
| `reasoning` | thinking (detail left alone) |
| `agent_message` | responding |
| `error` | **deliberately not shown** — Codex reports run diagnostics ("Skill descriptions were shortened") as `error` items; a real failure arrives as the top-level `error` event plus `turn.failed` |
| anything else | `humanizeToolName(type)` → executing, then satisfied `done` |

Only `turn.failed` breaks the streak, once per turn (a per-turn `streakBrokenThisTurn` flag cleared by `turn.started`). A top-level `error` is shown but not counted: codex 0.146 emits one for every *retryable* stream error ("Reconnecting... 1/5" — `will_retry: true` in the app-server protocol) and carries on, while a real failure always ends in `turn.failed`. Nothing runs after `finishSession`: `handleEvent` returns at once, because codex keeps printing while it shuts down after a forwarded signal and a late item used to rewrite the retired session as live. The child's `close` event, not `exit`, ends the run, so buffered stdout (including `turn.completed`) is drained rather than discarded — but `close` waits for every holder of the stdout pipe, so once codex has *exited* an `EXIT_GRACE_MS` (3s) timer ends the run anyway: a process codex (or a shell shim in front of it) left in the background used to block the user's terminal, the session unretired, for its whole life.

The session id is codex's **bare** thread id — the same `session_id` its native hooks carry (the pre-`thread.started` placeholder stays `codex-<pid>`). `setup.js codex` installs the hooks *and* suggests the wrapper for `codex exec`, which runs those hooks too, so each run used to be two sessions with every tool call, the daily session count and the streak counted twice. Now the wrapper goes quiet once it sees the hooks writing that session (`hooksAreLive()`: the file names editor `codex`, a pid that is not the wrapper's — a hook's is codex's, or absent on win32 — and a timestamp from this run): it stops writing what the hooks report more precisely (`HOOK_COVERED`: thread/turn starts, turn completion, items), keeps what they never see (`turn.failed`, retry notices, the end of the run), and ends the run on the hooks' own last frame, attention stamp and model. The session-ending write happens once (`finishSession`), from `close` or from a caught SIGINT/SIGTERM, which is also forwarded to codex; the pure `closeOutcome()` turns a signal-killed codex into an error and the exit code into 128+N (`signalExitCode` in base-adapter.js). `engmux-adapter.js` follows the same rules: a signal writes `error` / `interrupted` with `stopped` and exits 130/143.

#### The OpenCode 1.18 plugin contract

`adapters/opencode-plugin.mjs` is the shipped plugin; it feeds `opencode-adapter.js`. The contract is narrow and easy to get wrong:

- Bus events arrive **only** through `event({ event })` — registering `session.idle` and friends as top-level hooks (what the old documented snippet did) silently receives nothing.
- `tool.execute.before` gets its args in **output** (`output.args`), while `tool.execute.after` gets them in **input**.
- `tool.execute.after` is not called for a tool that throws; the failed `message.part.updated` covers that case (`tool.error`).
- **Every named export is invoked as a plugin factory**, so the module exports exactly one function — a second export, even a pure helper, kills plugin loading with `null is not an object (evaluating 'N.config')`. `translate()` hangs off the factory so tests can still reach it.
- `session.idle` / `session.error` are written **synchronously** (`spawnSync`), because `opencode run` exits with the turn and would take a fire-and-forget child with it. Everything else is fire-and-forget so the face can never block OpenCode — but one child at a time per session: payloads arriving while a child runs queue and go out as **one batch** (a JSON array; `processStdinEvent` applies each element in order) when it closes, at most `CHAIN_WAIT_MS` (3s) later, because two detached children raced for the stats lock and a fast tool's `after` could land before its `before`, leaving the face on "still running". The sync turn-end payloads take the session's queue with them in the same `spawnSync` batch, turn end last — queued events spawning after it re-opened the turn. The spawn promise never rejects (under EMFILE a child comes back with no stdin), and reasoning deltas are throttled per session (5s) so a streaming turn does not spawn a node process per delta.
- The node binary is resolved **per spawn** via `CODE_CRUMB_NODE || 'node'`, not captured at module load — OpenCode loads a plugin once at startup, and `process.execPath` inside it is the Bun binary.
- The adapter reads at most 1 MB of stdin and judges anything bigger from its raw text alone, so a batch over the cap lost every event in it. No tool argument may exceed `MAX_FIELD` (64 KB; `capInput` keeps a long string's **line count** as bare newlines, since the adapter counts a write's lines for its "+N" thought), and a batch is cut at `MAX_BATCH_BYTES` (900 KB; `takeBatch`, at least one item) — on the sync path too, as sequential `spawnSync`s with the turn end in the last.
- Every payload is numbered: `seq` in the order OpenCode reported it, `pluginId` per plugin instance. A child spawned just before a synchronous turn end cannot write before it (the `spawnSync` blocks the event loop that would feed the child's stdin), so its batch used to land after the turn end and re-open the turn. A turn end now records its `endSeq`/`pluginId` on the session file (carried on later writes), and the adapter treats a payload numbered before it as a **straggler**: it still counts in the stats but does not draw (a late tool end keeps its own rule).
- **Child sessions.** The task tool runs each delegated task in a child session (`sessions.create({ parentID })`); `session.created` is the only event that names the parent, so the plugin remembers it (`parentBySession`) and stamps `parentSession` on the child's later payloads, and the adapter keeps it on the child's session file. A child is an orbital of its parent, like a Claude Code subagent: it never stamps attention (every task used to take the center from the session that launched it), never writes the global file, counts its tool calls toward the parent (`statsId`), and its `session.idle` retires it (`stopped`).

State mapping: `session.created` → starting, reasoning → thinking, `permission.asked` (and the older `permission.updated`) → waiting `allow?`, `permission.replied` → satisfied (`answered`), `tool.error` → error, `session.idle` → happy + `stopped`.

**Every adapter** (base-adapter.js) coerces its identity fields — `sessionId`, `modelName`, `editor` — to text (`toText`): an object `session_id` keyed the renderer's faces by a fresh object on every load, a number read as a legacy row index in the session list, and an object `model_name` crashed the renderer. Timestamps are strictly increasing within a process (`nextTimestamp`), so a batch element written in the same millisecond as the one before is still newer to the renderer. A payload over 1 MB reaches the **session file** too, with its sticky fields, and is judged by its own event (read out of the raw text): only a tool end is checked for errors (a huge Write whose content said "exit code 2" put a false error on the global file), a tool start shows its tool, anything else thinks.

Root cause of #120 (phantom orbitals): the old documented snippet registered bus events as top-level hooks and captured an always-empty `session_id`, so every event fell back to `opencode-<ppid>` — and that ppid was a fresh `cmd.exe` shim per event.

## Code Conventions

- **Strict mode**: Every file starts with `'use strict'`
- **CommonJS**: Uses `require()` / no ES modules — the one exception is `adapters/opencode-plugin.mjs`, which OpenCode's Bun runtime loads as ESM
- **Layout**: a new module goes in `lib/`; the root is only for entry points that something runs by path (see File Structure)
- **Header blocks**: Each file has a boxed comment header explaining its purpose
- **Section dividers**: Logical sections separated by `// -- Section Name ---...` comments
- **Silent failures in hooks**: Hook code (update-state.js, adapters) wraps all I/O in try-catch and never throws — the editor must not be interrupted by a broken face
- **Atomic writes**: never `fs.writeFileSync` a state/session/stats/prefs/settings file directly — use `writeJsonAtomic` from shared.js (setup.js also writes a `.bak` first and aborts on unreadable/invalid JSON rather than replacing it; `codex-notify` does the same for `config.toml`, treating only `ENOENT` as "no config")
- **Whitespace and headers**: no trailing whitespace anywhere; every file's boxed header has its `|` rail aligned to the `+===+` border; non-ASCII glyphs in code strings use `uXXXX` escapes, **control characters included — never a raw NUL** (grid.js's group-cache separator is `\u0000`, so git and ripgrep treat the file as text). Comments may use literal Unicode.
- **Cross-platform paths**: Uses `process.env.USERPROFILE || process.env.HOME` and normalizes backslashes to forward slashes
- **No external dependencies**: All functionality is built with Node.js built-in modules (`fs`, `path`, `child_process`)
- **Line endings**: `.gitattributes` pins LF for everything except `*.cmd` (CRLF for cmd.exe); `.editorconfig` mirrors it (2-space, LF, trailing whitespace trimmed). Shebang files (`launch.js`, `setup.js`, `update-state.js`, `renderer.js`, `demo/*.js`, `tests/run.js`, `code-crumb.sh`, `adapters/*.js` except `base-adapter.js`) carry the executable bit in the index.

## Environment Variables

- `CODE_CRUMB_STATE` — override the global state file path (default: `~/.code-crumb-state`). It affects the hook writers and tmux mode only; the unified renderer's main face follows the chosen session's file under `~/.code-crumb-sessions/` regardless of this setting
- `CLAUDE_SESSION_ID` — set the session identifier (default: `<editor>-<parent PID>`, e.g. `claude-47040`; see Editor Provenance)
- `CODE_CRUMB_MODEL` — override the **display name** (`modelName`) in the status line (default: `claude`; adapters default to `codex`/`opencode`/`openclaw`). It does **not** override `model`, the real model identity — a known `model` outranks it on the status line (see Model Identity)
- `CODE_CRUMB_EDITOR` — override the editor provenance tag shown in the session list; beats the `--editor <name>` hook argument (default: `claude` in update-state.js; adapters set their own identity)
- `CODE_CRUMB_NODE` — the node binary the OpenCode plugin spawns for the adapter (default: `node` on PATH). Needed because `process.execPath` inside OpenCode is the Bun binary. Resolved per spawn, not at plugin load.
- `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` — set to `1` to enable Claude Code agent teams; Code Crumb will automatically detect teammate sessions via `TeammateIdle`/`TaskCompleted` hooks and show them in the orbital display with role labels and team-specific colors
- `NO_COLOR` — disable colour output in the renderer (also disables the `t` palette key)
- `MINIMAL_BOOT` — start the renderer in minimal mode (same as the `--minimal` flag)
- `ENGMUX_PYTHON` / `PYTHON` — interpreter used by `adapters/engmux-adapter.js` (default `python` on Windows, `python3` elsewhere)

Renderer CLI flags: `--minimal` (face + status only, no chrome, only `space`/`q` keys), `--tmux` (write a one-line status file for tmux instead of drawing; the state decays via the pure `tmuxDisplayState` — `waiting` held to `WAIT_HOLD_STALE_MS`, a stopped turn rests after `IDLE_TIMEOUT`, a tool after `LONG_TOOL_HOLD_MS`, anything else after `THINKING_TIMEOUT`), `--no-color`.

### Automated Tests

Run `npm test` (or `node tests/run.js [--quiet] [filter...]`, e.g. `node tests/run.js grid face`). Before loading anything the runner redirects `HOME`, `USERPROFILE`, and `CODE_CRUMB_STATE` to a throwaway directory (removed on exit), so the suite never touches the real `~/.code-crumb*` files or fights a running renderer — subprocess tests inherit the same env. Each test file gets its own counters from `tests/_harness.js` (`createSuite()`); `test.async` (or a test that returns a promise) is awaited before the file is counted, so async assertions can actually fail. ## Important Constraints

- **Hook performance**: update-state.js must complete in ~50ms — it runs synchronously in the editor hook pipeline. The stats lock costs ~0.3ms median uncontended against that budget, and a failed acquire proceeds unlocked rather than waiting.
- **State file size**: a realistic state write is ~750–950 bytes (`frequentFiles`, `cwd`, `gitBranch` and the stats fields account for most of it); keep it around 1 KB and never embed tool output
- **Terminal minimum size**: Main face requires 38x20 chars (`MIN_COLS_SINGLE`/`MIN_ROWS_SINGLE` in face.js; below that a "resize me" fallback is drawn and `lastPos` is cleared). Orbitals have no fixed minimum: `computeOrbit` in grid.js derives the ellipse from the space around the main face's worst-case keep-out and yields `maxSlots: 0` when nothing fits, which falls back to the side panel (see Orbit Geometry). Nothing may be written to the last cell of the last row — a wrap there scrolls the screen. Every layout width is in **terminal columns**, not code units: text that can come from a file or a tool (detail, task, label, cwd, branch, model, editor, thought text) is measured with `strWidth` and cut with `sliceToWidth` / `sliceFromEndToWidth` (shared.js: East Asian Wide/Fullwidth and default-emoji code points are 2, combining marks, ZWJ and variation selectors 0). A CJK folder used to push orbital rows to 16 columns in an 8-column box and the session list's border out by 10–18 columns; every glyph the app itself draws is pinned at width 1 by a test
- **No network**: All IPC is file-based, no sockets or HTTP
- **Graceful degradation**: Renderer handles terminal resize, missing state files, and stale sessions without crashing

## Known Follow-ups

- **A subagent's model comes from an undocumented file format.** The *directory* layout (`<projects>/<project>/<sessionId>/subagents/agent-<agentId>.jsonl`) is documented; the JSONL inside it is not. `_readTranscriptModel` treats it as a scraping target — bounded, guarded, silent on every failure — so a shape change costs a missing model on the orbitals and nothing else. There is no supported alternative: `SubagentStart` carries no model. (`subagentStatusLine` does expose a resolved per-task model, but taking it means taking over that UI row.)
- **`SubagentStart` does not carry `invocation_prompt` / `invocation_method`.** This document said it did. Against Claude Code 2.1.274's own hook schema the payload is `{hook_event_name, agent_id, agent_type}` and nothing else, which matches an open upstream docs bug. `subagentLabel` still reads `description` / `invocation_prompt` / `prompt` and so always falls through to `agent_type` for Claude Code — harmless, but it means the orbital label is the agent type, not the task, and the fallback chain is doing nothing it was written to do.
- **A `/model` switch needs the hooks re-registered.** `PostModelSwitch` is the 22nd event; an install predating it will not fire it, so those sessions follow the model only through `SessionStart` and the `Stop` tail-read. `npm run setup` fixes it.
- **The OpenCode model path is unverified.** `message.updated` → `properties.info.modelID` is the documented SDK shape, but nobody has watched a real one go past a running OpenCode. Every branch is guarded; a wrong guess yields no model and changes nothing else.
- **engmux is deliberately not wired up.** `engmux-adapter.js` already parses `-m`/`--model` into `modelName`; mapping it into `model` is one line plus the `'engmux'` sentinel filter (`extractModel` returns that literal when no flag is present, and `tests/test-adapters.js` pins it). Left out of the model change on purpose.
- **Screen clearing**: `renderer.js` clears the whole screen every frame (`ansi.home + ansi.clearBelow`, inside a DEC 2026 synchronized block) — that is now the single clearing mechanism. The old incremental clear buffers (`particles.clearPrevious`, `OrbitalSystem._buildClearBuf`, the 21-row band in `face.js`, `prevSessionListClear`, `_prevHelpBounds`) were removed as dead work, cutting a representative frame from 4027.9 to 2326.5 bytes (−42.2%). **A cross-terminal flicker check is still pending** — that one has to be done by eye and nobody has done it.
- **Unverified: a Windows Terminal `new-tab` from autolaunch may take focus from the editor's tab.** `wt -w 0 new-tab` opens the face in the current window; whether it steals keyboard focus mid-typing has not been checked on a live Windows machine. A `--focus`-less alternative (a separate window, `wt -w new`) would avoid it at the cost of a new window.
- **Unverified: an agent-teams teammate may take the center until its first `TeammateIdle`.** If teammates fire `SessionStart` through the shared hook config, their `SessionStart` stamps `lastPromptAt` before anything marks them `isTeammate`. Reproduced only with synthetic hooks; whether Claude Code actually sends a teammate's `SessionStart` there is unknown.
- **`pickMainSession` ranks by raw `lastPromptAt`.** After the clock steps back, a session prompted before the step keeps the center until the clock catches up (the apply path tolerates future stamps via `isNewerWrite`; the policy does not). Low.
- **An old renderer running across an upgrade never heartbeats.** On win32 its PID file goes stale after 60s and autolaunch can open a second face once; restarting the renderer after upgrading avoids it.
- **A background agent's result names its model.** Claude Code's `async_launched` Agent result carries `resolvedModel` — the agent's model, available at launch — which could replace the transcript scrape below for background agents. Not taken yet.
- **A lone subagent still vanishes at 120s during a long model turn.** Only *agent* writes heartbeat the parent's file, so when a whole family goes silent — one agent, thinking for over two minutes — nothing refreshes anything and the child window caps at `STALE_MS` instead of `CHILD_ORPHAN_TIMEOUT`. Accepted rather than fixed: on win32 there is no `pid`, so a long think is genuinely indistinguishable from a crash and the only lever is the timeout length. A ghost orbital animating fake work for 15 minutes is worse and more confusing than an orbital that disappears early during a real silence, and this is not a regression (the baseline was 90s/120s). Multi-agent families — the reported symptom — are fully protected. A real fix needs a usable liveness signal on Windows. (On Unix the editor's pid protects a silent agent, but only for `CHILD_ORPHAN_TIMEOUT` past its last write — `pidProtects` — so a missed `SubagentStop` cannot keep a ghost for the editor's lifetime.)
- **`daily.cumulativeMs` sums per-session time**, so windows open at the same time add up (it is "session time", not wall-clock time).
- **`UserPromptSubmit`/`Stop` register a session as top-level.** A legacy host whose subagents fire `Stop` under their *own* session id (no `agent_id`) would get those subagents registered as top-level windows.
- **A real agent orbital no longer fakes activity.** Cycling is off for `-agent-` orbitals, so during a long silent model turn one goes thinking → idle (45s) → sleeping (60s) instead of animating invented work. Honest, but less lively.
- **The `wt` `\;` escape is unverified against a live Windows Terminal.** It follows wt's documented escape and is pinned by a unit test, but nobody has opened a tab from a `;`-bearing path.
- **The codex-wrapper's spawn-`error` path** still exits without a final session write; harmless today because only the global file exists at that point.
- **`adapters/engmux-adapter.js` spawns python without `shell: true`**, so a `.cmd` shim or a Windows Store python alias cannot be spawned at all — the same bug class fixed for codex in `buildEditorSpawn`. Narrow impact (engmux has no setup/launch entry point), but real for some users.
- **Four `StopFailure` branches are unasserted**: `max_output_tokens`, `authentication_failed`, `billing_error`, and the `errorType || 'API error'` default. Four table rows. Declined during the 1.2.0 round because that would be *new* coverage in a task whose mandate was not to lower existing coverage — cheap to add whenever someone wants those four error faces pinned.
- **Two `fs.watch` handles on the same sessions directory.** `stateWatcher` (main-file changes, 50ms leading-edge throttle) and `sessionWatcher` (any change, 80ms trailing debounce) both watch `SESSIONS_DIR`; before the main face moved onto a session file they watched two different paths. One watcher fanning out to both callbacks would be cheaper.
- **`codex-notify.js` never stamps `lastPromptAt`.** Its only event is a turn end, so a notify-only Codex session has no attention stamp at all and can only reach the center when nothing else is competing (the newest-write tiebreak). Correct as far as it goes — there is no event there that means "the user just prompted".
- **Hook paths are only double-quoted.** `buildFaceHooks`/`buildCodexHooks` write `node "<path>" <Event>`, so a checkout under a folder whose name contains `$` or a backtick is expanded by the shell and the hook fails to find update-state.js. Left alone in the third review pass: escaping `$` for POSIX shells would break the same command wherever it runs under cmd.exe, and such paths are rare.
- **Unconfirmed, below the bar in the Sep 2026 review:** the orbital `+N more` text (`grid.js`, `mainPos.row + mainPos.h + 7`) can overdraw the lowest ring face once per rotation when there are more sessions than `maxSlots`.
- **`quoteArg` (win32 `shell: true`) cannot neutralise `!VAR!`** if delayed expansion is enabled in the registry (off by default for `cmd /c`). Every other cmd metacharacter is quoted, an embedded `"` becomes `""`, `%` is emitted as `"^%"`, and line breaks become spaces. The `wt` launch additionally escapes `;` as `\;` (`wtEscape` in shared.js), because Windows Terminal splits subcommands on `;` even inside quotes.
- **`docs/` is gitignored.** The attention-main spec and plan live untracked in `docs/superpowers/specs/2026-09-09-attention-main-design.md` and `docs/superpowers/plans/2026-09-09-attention-main.md` — they are not in the repository and will not survive a fresh clone.
- **`MAX_ORBITALS` is 8.** Now that every Claude Code subagent gets its own orbital, a user running more than eight agents sees only the first eight. Previously they saw none, so this is the new visible ceiling rather than a regression.
- **engmux** has an adapter but no `setup`/`launch` entry point; invoke `adapters/engmux-adapter.js` directly.
- A state file without a `timestamp` is never applied by the renderer (`ts > lastAppliedTimestamp` with both 0). Every writer stamps one, so this only affects hand-written files.
